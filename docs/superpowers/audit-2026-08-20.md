## 1. Bugs

### 🔴 Le raccourci de recherche est inopérant

`useKeyboardNav.ts:83` — la touche `F` fait :
```ts
const searchInput = document.querySelector<HTMLElement>('[data-search-input]');
if (searchInput) searchInput.focus();
```
Or cet `<input>` n'est rendu **que lorsque la recherche est déjà ouverte**
(`ArticleList.tsx:444`, à l'intérieur du bloc `searchOpen`). Dans l'état normal —
recherche fermée — la requête retourne `null` et **le raccourci ne fait rien**.

`ArticleList.tsx:213` contient l'effet manifestement destiné à faire le pont :
il écoute `focus` sur ce même élément pour appeler `setSearchOpen(true)`. Il
s'exécute au montage, quand l'élément n'existe pas non plus : l'écouteur n'est
donc **jamais attaché**.

**Correctif** : la touche doit appeler `setSearchOpen(true)` (via le store ou un
évènement), et non tenter de focaliser un élément absent. L'effet du pont
devient alors inutile et doit disparaître.

### 🟠 Écouteur sans nettoyage

Le même effet `ArticleList.tsx:213` n'a **pas de fonction de retour** :
```ts
if (el) el.addEventListener('focus', handler);   // jamais retiré
```
Sans effet aujourd'hui puisqu'il ne s'attache jamais — mais si le correctif
ci-dessus rendait l'élément présent au montage, chaque remontage de la liste
ajouterait un écouteur définitif.

### ✅ Vérifié sain

- **Aucune fuite de minuteur** : aucun `setInterval` sans `clearInterval`.
- **Écouteurs tactiles** (liste et volet de lecture) : tous retirés au démontage.
- **`{ once: true }`** sur les évènements d'image : auto-retirés, faux positifs
  d'un décompte naïf.

## 3. Sécurité

### ✅ Points solides

- **0 vulnérabilité** dans les dépendances de production (`npm audit`).
- **Aucun `eval` ni `new Function`**.
- **Injection HTML maîtrisée** : les 3 `dangerouslySetInnerHTML` reçoivent soit
  du HTML passé par DOMPurify, soit un balisage que l'app construit elle-même.
  Un test verrouille l'invariant (`youtubeFacade.sanitize.test.ts`).
- **SQL paramétré** : la seule interpolation est
  `PRAGMA table_info(${table})` (`db.ts:74`), appelée exclusivement avec deux
  littéraux internes (`'users'`). Aucune entrée utilisateur n'y accède.
- **Garde anti-SSRF** sur le proxy, avec tests dédiés (`proxy.test.ts`).
- **CSP stricte** : `script-src 'self'`, `connect-src 'self'`,
  `object-src 'none'`, `frame-ancestors 'none'`.

### 🔴 La déconnexion n'invalidait pas la session serveur — corrigé

`authStore.logoutBackend` ne faisait que vider le `localStorage`. La ligne
correspondante dans la table `sessions` restait en base : **un jeton capturé
avant la déconnexion continuait de fonctionner** jusqu'à son expiration.

La route `POST /api/auth/logout` existait et supprimait bien la session
(`auth.ts:176`), et le client possédait même le wrapper `logoutUser()` — jamais
appelé. C'est ce qui l'avait fait classer en « code mort » au premier passage.

**Corrigé** : la déconnexion appelle l'endpoint avec le jeton capturé avant
effacement, en « au mieux » (l'état local est vidé quoi qu'il arrive, y compris
hors ligne).

### 🟡 Compromis à connaître

- **JWT en `localStorage`** (`authStore.ts:42`). Exposé à toute XSS. C'est
  l'usage courant des applications de ce type, et la CSP réduit fortement le
  risque ; un cookie `HttpOnly` serait plus sûr mais imposerait une gestion CSRF.
  À documenter comme choix assumé plutôt qu'à corriger dans l'urgence.
- **Le référent envoyé pour les images** (préchargement hors ligne) est dérivé de
  la cible côté serveur, jamais fourni par le client — vérifié, pas de falsification
  possible.

## 4. Optimisation

### Poids livré

| Fichier | Taille |
|---|---|
| `index.js` | **516 Ko** |
| `Preferences.js` | 68 Ko (déjà chargé à la demande) |
| `extractContent.js` | 36 Ko (déjà chargé à la demande) |
| Locales | ~20 Ko chacune, chargées séparément |
| **Total JS** | **784 Ko** |

Le découpage est déjà correct : préférences, extraction et langues sont hors du
bundle principal.

### 🟡 Pistes, par rapport gain/effort

1. **`Preferences.tsx` fait 3010 lignes** — de loin le plus gros fichier du
   projet. Il mélange huit onglets sans rapport entre eux. Le découper par onglet
   améliorerait autant la lisibilité que le chargement. **C'est aussi le fichier
   dont tu veux refondre l'interface** : les deux travaux se rejoignent.
2. **`index.js` : composition mesurée le 2026-08-20** (via les cartes de source,
   sans ajouter de dépendance) — 510 Ko attribués :

   | Part | Poids | |
   |---|---|---|
   | Code FriRSS | 227 Ko | 44,6 % |
   | react-dom | 129 Ko | 25,3 % |
   | axios | 48 Ko | 9,4 % |
   | i18next | 43 Ko | 8,5 % |
   | dompurify | 29 Ko | 5,7 % |
   | react-i18next | 21 Ko | 4,0 % |

   **Conclusion : rien d'anormal, aucun gain facile.** Aucune bibliothèque
   surdimensionnée pour son usage. Le seul candidat théorique est **axios
   (48 Ko)**, remplaçable par `fetch` — mais ses intercepteurs portent la
   réécriture vers `/api/proxy` et l'injection du JWT : il faudrait les
   réimplémenter, pour ~9 % du bundle. À ne pas entreprendre sans autre raison.

   Les trois plus gros fichiers du projet — `Sidebar` (42 Ko), `ReadingPane`
   (38 Ko), `ArticleList` (29 Ko) — sont du code utile, pas du poids mort.
3. `Sidebar.tsx` (1706 lignes) et `ReadingPane.tsx` (1576) approchent le seuil où
   la relecture devient coûteuse, sans être critiques.
